## `services/gates-kubeconfig/` — every host side effect and remote dependency (first Ansible role)

Files: `README.md`, `install.sh`, `refresh-gates-kubeconfig`, `with-gates-kubeconfig`. Merged; never executed on `vps`.

Host side effects, in execution order of `sudo ./install.sh`:

1. `mktemp -d` scratch (removed on EXIT trap); `dpkg --print-architecture` to pick the arch.
2. GET `https://dl.k8s.io/release/v1.36.2/bin/linux/<arch>/kubectl` and `…/kubectl.sha256`; `sha256sum --check` against the PUBLISHED digest; `install -m 0755 → /usr/local/bin/kubectl`. Skipped when the installed `kubectl version --client` already contains `v1.36.2`.
3. `install -m 0755 → /usr/local/bin/refresh-gates-kubeconfig` and `/usr/local/bin/with-gates-kubeconfig` (unconditional overwrite; no daemon, no unit, no timer — refresh-on-401 is deliberate, "Refresh on a schedule? No").
4. Determine `FETCH_USER = ${SUDO_USER:-${USER:-root}}`. If `sudo -u $FETCH_USER sudo -n true` succeeds (that user has passwordless sudo), run `sudo -u $FETCH_USER /usr/local/bin/refresh-gates-kubeconfig`; a failure only WARNs. Otherwise prints SKIPPED.
5. `refresh-gates-kubeconfig` then: `ssh -o BatchMode=yes -o ConnectTimeout=15 poweredge-xubuntu "sudo cat /etc/ci-runner/gates.kubeconfig"` into a shell variable (no temp file); validates `^kind: Config$` and `server:`; `install -d -m 0755 /etc/ci-runner`; `printf | install -m 0600 /dev/stdin /etc/ci-runner/gates.kubeconfig`; `unset rendered`. On any failure it writes nothing and exits 1.
6. Verify: `kubectl version --client`; `stat` the kubeconfig (mode/owner/size only, content never printed); `sudo -u $FETCH_USER env KUBECONFIG=/etc/ci-runner/gates.kubeconfig kubectl auth can-i create jobs -n gates` — an authorisation probe that creates no Job. A `no`/error only WARNs.

Remote / ssh dependencies:

- ssh host `poweredge-xubuntu` must resolve for `$FETCH_USER` (tailnet MagicDNS `poweredge-xubuntu.perch-rudd.ts.net` or an `~/.ssh/config` alias) with a key already authorised there (`BatchMode=yes` → no prompts), and that remote user needs passwordless `sudo` for `cat /etc/ci-runner/gates.kubeconfig`.
- poweredge's `converge-ci-stack.service` must have rendered `/etc/ci-runner/gates.kubeconfig` (the README troubleshooting step). The credential is a bearer token for the `gates` namespace `gate-submitter` ServiceAccount; RBAC is committed in `livespec-dev-tooling` `ci-runner/k3s/phase2/gates/gates-rbac.yaml`.
- The token is regenerated at every poweredge boot (tmpfs k3s datastore), so the file on `vps` is expected to go stale; `with-gates-kubeconfig` re-pulls once on a 401.
- Network: egress to `dl.k8s.io` (install only) and to the API server `https://poweredge-xubuntu.perch-rudd.ts.net:6443` over the tailnet (verify + every use).
- Env overrides honoured: `GATES_REMOTE_HOST`, `GATES_REMOTE_KUBECONFIG`, `GATES_KUBECONFIG`, `GATES_REFRESH_BIN`.

Two defects to resolve in the role rather than port verbatim (both visible only by reading, since it has never run):

- **Local privilege mismatch in the fetch.** `install.sh`'s comment says the refresh script "is re-elevated inside — hence `sudo -u … sudo`", but `refresh-gates-kubeconfig` contains NO local `sudo`: its only `sudo` is the REMOTE `sudo cat`. Run as `ubuntu` (which is what `sudo -u $SUDO_USER` does), `install -d /etc/ci-runner` and the `install -m 0600 … /etc/ci-runner/gates.kubeconfig` write will fail with permission denied, so step 4 will WARN on a fresh host. Run as root instead, the file lands `root:root 0600`, and then the step-6 verify (run as `ubuntu`) and any `ubuntu` caller of `with-gates-kubeconfig` cannot read it. The role must pick an owner (ubuntu:ubuntu 0600, or a group-readable variant) and create `/etc/ci-runner` with that owner explicitly.
- **Root-only `/etc/ci-runner` ownership is unspecified.** Nothing in the repo says who owns `/etc/ci-runner`; on `poweredge` it is converge-owned, on `vps` it does not exist yet.

## 3. CONVENTION (AGENTS.md at origin/master, verbatim excerpts)

`## Conventions`:

> - One service per directory under `services/`.
> - Each service has at minimum: `*.service` unit + idempotent `install.sh`. Larger services may add a per-service README. Config-only entries that tune an existing system service (e.g. `ssh-hardening`, which configures the OS `ssh.service` via a `sshd_config.d` drop-in) ship a config file + `install.sh` and have no unit of their own.
> - `install.sh` scripts MUST be idempotent — re-running them is the supported repair path. They should `set -euo pipefail`, write the managed file(s) (`sudo tee` for units, or `install -m` for config drop-ins), then `daemon-reload` + `enable --now` + a verification `systemctl is-active` (for unit services) or `sshd -t` + `systemctl reload` + an effective-config check (for config-only entries).
> - Document caveats per service in this AGENTS.md, not in the unit file. …

`## Rules` (the install-relevant one):

> - **Apt-installed services**: prefer the upstream's official apt repo for auto-updates over manual binaries (e.g., VS Code uses `https://packages.microsoft.com/repos/code`). When Microsoft's `code` package post-install hook drops its own `vscode.sources` file, defer to it — don't write a duplicate `vscode.list` …

How services are installed: every per-service "Install / re-install" block is a single command run from the checkout, e.g. `sudo /home/ubuntu/workspace/vps-info/services/<name>/install.sh` for root-scope services, and `/home/ubuntu/workspace/vps-info/services/<name>/install.sh   # no sudo — user-level config` for the user-scope ones (`claude-ntfy`, `claude-code-hooks`, `codex-config`, `honeycomb-mcp`, `tmux-config`). `README.md` "Quickstart" adds an ordering rule: "Run in order — the proxy depends on the editor backend: `sudo services/code-serve-web/install.sh` then `sudo services/code-pwa-proxy/install.sh`"; AGENTS.md adds "vnc-desktop must already be installed and active first" for `1password-desktop`, and `claude-desktop` warns if vnc-desktop is inactive.
