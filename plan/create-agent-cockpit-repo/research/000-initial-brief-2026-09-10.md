# Initial brief: create-agent-cockpit-repo

Recorded from the maintainer request on 2026-09-10.

Plan a new GitOps repository, `agent-cockpit-info`, that can reproduce an AI-agent-driving Ubuntu machine from a bare Linux instance and support multiple numbered instances named and hostnamed `agent-cockpit-{n}`, beginning with `agent-cockpit-0`. The target user is `ubuntu`; repositories clone directly into `/home/ubuntu/workspace`, not `/data/projects` and not through a workspace symlink. The design should become cattle-like, with persistent state separated from replaceable machine configuration so later container or Kubernetes execution remains possible.

The new repository should retain the useful cockpit surface now present on the VPS: tmux configuration and session-driving ergonomics; Tailscale enrollment; the manually provisioned 1Password environment wrapper backed by its one baked systemd credential; custom Ctrl-R shell history; GitHub CLI/authentication; AWS CLI/configuration; Claude, Codex, and Pi; their shared configuration and MCP integrations; local VNC using the current window manager; Chrome and 1Password Desktop in that desktop; Honeycomb configuration and comprehensive observability for agent activity; and any other measured dependencies required for a usable cockpit. A GitOps-oriented machine config, tentatively `ai-cockpit-config.jsonc`, should carry at least the instance number/hostname and an initial auto-clone inventory derived from the repositories currently in `~/workspace`.

Explicit exclusions from the new generic cockpit are host-bespoke workloads: Dolt server and its backup/launch services, local Fabro server instances, VS Code/code-serve-web, VPS filesystem backup systems, and other single-host services that cannot be multiplied. The plan must classify the existing `vps-info` and agent-flywheel surfaces rather than copy them indiscriminately.

Before choosing the repository architecture, compare a standalone Ansible repo patterned after `hp-xubuntu-info`, `poweredge-xubuntu-info`, and `gmktec-xubuntu-info` with a full LiveSpec ecosystem member such as `livespec-agent-cockpit`. Determine how much those host repos actually depend on `livespec` or `livespec-dev-tooling`, reuse rather than duplicate mature GitOps/Ansible primitives where that dependency is justified, and obtain independent Fable-seat and Sol critiques of the tradeoffs before finalizing the plan.

The migration must provision a new VPS, bring up and dogfood one new cockpit, transfer active agent-driving work safely, then deprecate duplicated cockpit files and responsibilities from `vps-info` and stop using the current VPS as a cockpit. The intended residue in `vps-info` is its bespoke server role, principally Dolt and genuinely VPS-specific services; deprecation must follow proven replacement, not precede it.
