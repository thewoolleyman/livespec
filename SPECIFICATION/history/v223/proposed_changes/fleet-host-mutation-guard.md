## Proposal: Every Driver ships a fleet-host mutation guard denying positively-identified hand changes to fleet-managed hosts outside the sanctioned apply

### Target specification files

- SPECIFICATION/contracts.md
- SPECIFICATION/scenarios.md

### Summary

Add a REQUIRED fleet-host mutation guard to SPECIFICATION/contracts.md §"Driver-shipped hooks" as three bold clauses in the shape of the existing footgun-guard clauses — a Claude clause plus Codex and pi sibling clauses. The clauses state the REQUIRED SURFACE and its behavioral discipline, not the guard's detection internals: what the guard MUST deny (a mutating `ssh`/`scp`/`rsync`/`sftp` reach to a fleet-managed host; a `kubectl` or `helm` verb outside the read-only set, regardless of host; an ad-hoc `ansible` run with privilege escalation; an uncommitted-playbook apply without `--check`); what it MUST NOT deny (the sanctioned apply and drift, read-only reaches, and any reach to a host outside the set); where the host set comes from (the provisioning inventory, never hardcoded, with a documented fallback, and host identity by full name or first DNS label); the negative-space rules for verb-taking tools and for a remote `sudo`; the remote-shell mutation signals as a non-exhaustive minimum the Driver MUST NOT narrow; payload-carrier inspection as a requirement; the stated known limits; the fail-closed-when-hinted posture, with depth exhaustion denied regardless; command-substitution judging; the existence of telemetry that never changes a verdict; the out-of-scope statements; the three protected home sub-trees; and the deny reason. The exact hint predicate, the verb and flag tables, the wrapper and payload grammar, the depth budget, and the telemetry scope are declared Driver-side detection internals the Driver documents and tunes. Four drift-sweep amendments keep the section self-consistent (the Claude bundle's hook count, the runtime-specific-hooks enumeration, the pi Driver's one-extension sentence, and the hook failure discipline's declared fail-closed exception, widened from one hook to the class, together with its non-livespec-projects rule, which names the guard as its one stated exception), and one `## ` scenario is added to scenarios.md with its tests/heading-coverage.json and tests/heading-coverage-debt.json entries.

### Motivation

Epic livespec-qurhq2, child livespec-vbqmdd (C1); design in livespec `plan/gitops-deployment-discipline/research/000-failures-root-causes-and-binding-fixes-2026-09-12.md` §3 (the row for failures 1 and 4). The instruction obligation in the sibling pending proposal `gitops-deployment-topic` (split from the former combined proposal `gitops-deployment-discipline`, deferred to the follow-up plan) tells an agent to read the provisioning model before touching a host; this guard is its mechanical half — the same instruction-plus-mechanism pairing the section already applies to `--no-verify` (footgun guard) and to local-memory writes (auto-memory guard). The hand reaches of the session described in that sibling proposal's motivation were ordinary `ssh` commands from a governed session, exactly the shape a `PreToolUse` guard on the shell tool intercepts. The host set is read from the provisioning inventory because the inventory is the committed statement of which hosts the automation owns, and a hardcoded list in a hook would be the inverted-layer defect (a copy maintained beside its source) this epic exists to remove. The Claude guard is child livespec-ggs36t (C3), built in parallel and merged only after this clause ratifies; the Codex and pi sibling guards have no ledger item yet and MUST be filed as follow-ups under the epic when this proposal is accepted. The scenario is added because the propose-change authoring discipline requires load-bearing behavior to carry a `## Scenario`, and the section's own precedent — the primary-checkout Playwright guard — carries one (`## Primary-checkout Playwright calls are refused`) mapped through tests/heading-coverage.json to an integration-tier lockstep test.

The inserted paragraphs, verbatim:

> **Fleet-host mutation guard (required).** The Claude Code Driver (`livespec-driver-claude`) MUST ship a `PreToolUse` hook registered on the `Bash` tool that denies a POSITIVELY-IDENTIFIED hand change from an agent session to a fleet-managed host — the mechanical half of the GitOps deployment discipline: a live fleet host is changed only by the committed automation applied from its control node, never by hand from a session. The guard judges every command the shell would run — each `;`, `&&`, `||`, and pipeline segment, reached through wrapper prefixes such as `env`, `timeout`, or `sh -c` — and MUST deny: (a) a remote reach — an `ssh`, `scp`, `rsync`, or `sftp` whose target is a fleet-managed host — whose remote command or transferred payload is mutating; (b) a `kubectl` or `helm` verb outside that tool's read-only set, regardless of which host the session or the command names, exempted ONLY by a `--dry-run` whose value is other than `none` or `false`; (c) an ad-hoc `ansible` run with privilege escalation (`-b`/`--become`), or with a module the Driver documents as mutating; and (d) an uncommitted-playbook apply without `--check`, as stated with the sanctioned set below. Verb-taking tools are judged by NEGATIVE SPACE — `kubectl` and `helm` wherever they run, and inside a remote command at least `systemctl`, `git`, `k3s`, `crictl`, `ctr`, `docker`, `tailscale`, and the package managers `apt`, `apt-get`, `snap`, `pip`, and `npm`: the Driver enumerates each tool's READ-ONLY verbs and convicts every other verb, so `kubectl apply`, `delete`, `drain`, or `exec` is denied because it is not a read, not because a mutating list names it, and a verb a tool grows later is denied until the Driver adds it to the read-only set (a Driver-side widening that needs no core spec cycle). Inside a remote command to a fleet-managed host, the mutating signals are a NON-EXHAUSTIVE minimum the Driver MAY widen and MUST NOT narrow: privilege escalation (`sudo`, under the negative-space rule below); a head that is itself a mutation, such as `install` (a mutation regardless of path), `reboot`, `useradd`, or `mkfs`; the path-scoped write heads `cp`, `mv`, `rm`, `rmdir`, `mkdir`, `touch`, `ln`, `truncate`, `tee`, `chmod`, `chown`, and `chgrp`, which are mutations when a written operand — the destination of `cp`, the source or destination of `mv`, any operand of the others — lies under a protected tree: `/etc`, `/usr`, `/opt`, `/var/lib`, `/srv`, `/boot`, or one of the three protected home sub-trees named in the scope decision below; output redirection into a protected tree; a verb-taking tool's verb outside its read-only set; and a mutating flag of a head that otherwise reads, such as `find -delete` or `-exec`, `sed -i`, `sysctl -w`, `iptables -A`, `journalctl --vacuum-size`, or an `nft` rule change (`nft -c`/`--check` alone is a check, not a rule change). A `scp` or `rsync` upload to a fleet host is a mutation unless it is an `rsync --dry-run` (`-n`); a download from a fleet host is a read, except an `rsync --remove-source-files`, which mutates the host. A remote `sudo` is governed by a NEGATIVE-SPACE rule: it is a mutation UNLESS the escalated command is on the guard's documented read-only allowlist or is a shell whose payload the guard judges as above, so an unlisted escalated command is denied rather than presumed harmless. The sanctioned set — the commands the guard MUST NOT deny — is exactly `just ansible-apply`, `just ansible-drift`, and `ansible-playbook` running a committed playbook, with or without `--check`. Sanctioning is judged on each segment's FIRST recognised command head only, so a sanctioned name appearing as an argument, after a remote-shell head, or inside a remote payload sanctions nothing. The sanction identifies rather than guesses: an `ansible-playbook` or `just ansible-apply` is denied as a hand deploy ONLY when a playbook operand is POSITIVELY outside committed source — a path under `~`, `/tmp`, `/var/tmp`, or `/dev/shm`, or one carrying `..` or a `$` — and the run does not carry `--check`; any other playbook path, relative or absolute (an absolute path into a repository checkout included), passes; an option value (`-i <inventory>`, `-e <vars>`, `--vault-password-file <file>`, and the like) is never a playbook; and `just ansible-drift` always passes. An ad-hoc `ansible … --become` is denied, not merely unsanctioned. A read-only reach MUST NOT be denied: an `ssh` whose remote command only inspects state (such as `cat`, `ls`, `stat`, `systemctl status`, a `journalctl` read, or `grep`), and a read verb of `kubectl` (such as `get`, `describe`, or `logs`) or of `helm`. Host identity: a target is a fleet-managed host when it matches in full, or by its first DNS label compared case-insensitively, an inventory host name, a `host_vars/<host>.yml` stem, or a DECLARED `ansible_host` value in the provisioning inventory — the governed project's own Ansible inventory when its tree carries one (a linked worktree resolves it through its primary checkout), else the fleet provisioning repository's (`livespec-dev-tooling`'s `ansible/inventory/`); the host set MUST NOT be hardcoded; a documented fallback to a named legacy host list is permitted ONLY when no inventory resolves, and the hook MUST name it as a fallback in its own documentation; and an IP address that no inventory entry declares as `ansible_host` is NOT recognized, an address held under any other variable included — a stated limit of this guard, not an omission. Payload carriers MUST be inspected for the same hazards as a direct command: `sh -c` and `bash <<<` payloads, an `eval`, `watch`, or `script -c` payload, the operands of tmux `new-session` and `send-keys`, and a script fed on standard input (from `echo`, `printf`, or a here-document) to `sftp`, `bash`, or `ssh … bash -s`; inside a remote command, a shell reading a script from a pipe the guard cannot read (`curl … | sh`) is a mutation. Stated known limits: interpreter payloads (`python3 -c …`), `sftp -b <file>` batch files, `sudo bash -s < file`, a script assembled in another language, a variable-target `scp`/`rsync`/`sftp` on a hinted command, and a loop over host names not present in the command text. Fail-closed when hinted: a command is HINTED when its lower-cased raw text contains one of the words `ssh`, `scp`, `rsync`, or `sftp` anywhere together with a fleet host name as a substring, or contains the word `kubectl` or `helm` together with one of the guard's documented cluster-mutating verbs; the exact predicate is a Driver-side detection internal, and a read-only command the hint catches and the guard then cannot resolve is a stated false positive the Driver tunes rather than a defect of this clause. On a hinted command the guard MUST deny what it cannot read — an unparseable segment, or a command head or reach target that is a shell VARIABLE or positional expansion it cannot resolve (`$var`, `{}`) — because a parser exhausted on a hinted command is evidence of evasion, not of safety; two qualifications: an unresolvable `ssh` target, whose remote payload is judged first, so a reach whose payload is non-empty and convicts nothing is ALLOWED; and an `scp`, `rsync`, or `sftp` whose host operand is a shell expansion the guard cannot resolve, which is a STATED LIMIT of this guard today (listed above) rather than a denial. Nesting beyond the guard's depth budget is denied whether or not the command is hinted, because nothing legitimate nests that deep. A command substitution (`$(…)`, backticks) is NOT blanket-denied: its contents are judged as commands in their own right, so `> /tmp/nodes-$(date +%s).txt` convicts nothing and `echo $(ssh host 'sudo x')` is a mutation when `host` is fleet-managed. Telemetry: the guard MUST write one telemetry record per command the guard judges in scope — at least every command it denies on its classification path — for allow and deny alike, and a telemetry failure MUST NOT change a verdict. Out of scope, stated so each is a commitment rather than an omission: a LOCAL (non-remote) mutation on the control node itself, which the committed automation's own playbooks perform and which no remote reach carries, except an ad-hoc `ansible` run with privilege escalation, which is a hand deploy whatever host it names; and — a SCOPE DECISION — an unprivileged user-level filesystem change on a fleet host under `/tmp`, `/var/tmp`, `/dev/shm`, or a user home (a `mkdir`, `touch`, `rm`, or `ln` without privilege; repositories, worktrees, and scratch under a home stay unpoliced), because the guard protects host CONFIGURATION — the protected trees named above, services, packages, and cluster state — not scratch. Three configuration sub-trees of a user home ARE protected like `/etc`, in every spelling (`~`, `$HOME`, `/home/<user>`, `/root`): `~/.ssh` (access control — `authorized_keys`), `~/.config/systemd` (user units), and `~/.fabro*` (the automation-managed Fabro server state, such as `.fabro` and `.fabro-mi-homelab`). The deny reason MUST name the GitOps deployment discipline and MUST name the sanctioned apply as the path to take instead; where the repository carries a `.ai/gitops-deployment*.md` topic, the reason MUST route the agent to it. The guard is a declared fail-closed guard hook under the hook failure discipline above: on a hook failure it denies a command whose raw hook input carries the hazard hint (judged against the documented fallback host list, because host-set resolution may be what failed) and silently passes every other command, exiting 0 on every path; and it acts only on a POSITIVE identification of one of the denials stated above — a mutating reach to a fleet-managed host, a `kubectl` or `helm` verb outside the read-only set, an uncommitted-playbook apply without `--check`, an ad-hoc `ansible` run with privilege escalation or a documented mutating module, a hazard-hinted segment it cannot resolve, or nesting beyond its depth budget — so an `ssh` to a host outside the set, a `kubectl` read, and a command matching none of these pass through. The guard applies in every project the Driver loads in, governed by livespec or not, because a fleet-managed host is fleet state whichever project the session runs in; it is the stated exception to this section's rule that hooks MUST NOT disturb non-livespec projects. The guard is footgun-prevention, not the isolation boundary (the isolation boundary is each host's own access control together with the committed automation's control node); like the beads-access guard, its purpose is to convert a silent hand change into an actionable block that names the committed path. Like the other Driver hooks, the script implementation, its command classifier, and their tests live in the Driver repo. The exact hint predicate, the read-only and mutating verb and flag tables, the wrapper and payload-carrier grammar, the depth budget, and the telemetry scope are Driver-side detection internals the Driver documents and tunes per the closing paragraph of this section, provided the denials, allowances, and postures stated here hold; this section states the required surface and its behavioral discipline.
