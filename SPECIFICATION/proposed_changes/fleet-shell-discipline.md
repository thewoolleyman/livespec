## Proposal: Governed shell and Justfile discipline

### Target specification files

- SPECIFICATION/non-functional-requirements.md
- SPECIFICATION/contracts.md

### Summary

Define one fleet-wide contributor convention for thin Justfiles, explicit shell execution policy, bounded error-handling exceptions, and complete ShellCheck coverage, with Gherkin scenarios in the existing non-functional Scenarios section so the rules are mechanically testable without changing the public livespec contract.

### Motivation

A fresh forge-backed census at 2026-08-02T22:58Z found 719 recipes across the nine governed repositories: 106 Bash-shebang bodies, 120 multiline bodies, 49 recipe bodies containing Just interpolation, and 49 tracked shell scripts. The current corpus mixes orchestration logic into Justfiles and uses several undeclared shell-option profiles, so review cannot distinguish intentional exceptions from drift. Core owns the inherited convention and enforcement semantics; the `livespec-dev-tooling` sibling owns building and shipping the shared verifier, choosing the ShellCheck acceptance floor, pinning the tool, and carrying fleet rollout through its replacement work-item slices.

### Proposed Changes

Under the existing `## Constraints` section, add `### Shell and Justfile discipline`. Define one governed shell-file universe exactly once as every tracked, non-vendored `.sh` file outside frozen archive paths, including template sources. Add these normative rules:

1. A governed Justfile MUST remain a task index: a recipe body MUST be empty or contain exactly one plain direct command line invoking an executable, another `just` entry point, or a tracked script; either form MAY also declare recipe dependencies. Recipe bodies MUST NOT contain shebang bodies, multiline shell programs, shell control flow, pipelines, redirections, command substitution, or command chaining. Just quiet syntax and leading environment assignments MAY decorate a line that is otherwise a conforming direct invocation.
2. Recipe bodies MUST NOT contain Just interpolation. A parameterized recipe MUST use a per-recipe positional-arguments declaration and quote positional shell parameters such as `$1` and `$@`; a global Just value needed by a script MUST be exported under an explicit environment-variable name. Enforcement MUST inspect Just's parsed JSON representation rather than grep source text, and its parser and invocation fixtures MUST execute from a real `zsh` caller.
3. Every file in the governed shell-file universe MUST declare its effective option policy before its first executable statement. Bash scripts MUST declare errexit, nounset, and pipefail; POSIX-sh scripts MUST declare errexit and nounset. A different policy MAY be used only when an adjacent non-empty rationale identifies the intentional semantics, including an aggregator that deliberately omits errexit to collect multiple failures. The file's shebang MUST select the dialect used to classify its canonical profile and to analyze it with ShellCheck.
4. A local errexit suspension MUST carry an immediate rationale, MUST immediately capture the suspended command's status, and MUST then restore errexit before any unrelated command runs.
5. Additional Bash settings such as noclobber, errtrace, and an ERR trap MAY be adopted when a script needs them but MUST NOT be universal requirements or require a sourced boilerplate dependency.
6. ShellCheck MUST analyze every file in the governed shell-file universe, and every violation outside the acceptance policy owned by the shared tool MUST fail the canonical check. The ShellCheck version pin, starting severity, baseline representation or absence, ratchet, and fleet rollout MUST be owned by the `livespec-dev-tooling` sibling specification, not duplicated in core. Tests of a governed shell file MUST invoke it under its declared shebang rather than substitute the caller's shell. The canonical shared verifier supplied by `livespec-dev-tooling` MUST enforce the inherited convention. Bringing an existing corpus into conformance MUST be the consumer's own conformance change, not part of the verifier.

Co-edit the existing `### Conformance Pattern` concern registry by adding **Shell-and-Justfile-discipline** to the `Further recognized members` paragraph with a pointer to the new constraint section. The complete five-slot expansion MUST live in that new section, following the existing Plugin-currency precedent, so the registry preamble continues to seed exactly two numbered concerns and its `concern #1` / `concern #2` enumeration remains unchanged. The new member's Contract MUST be the new constraint section; its Mechanism MUST be the conforming thin Justfile, tracked static check-target inventory, shared aggregate runner, and governed tracked shell files; its Installer MUST be the consumer bootstrap and pin-update path that installs the sibling-selected ShellCheck pin and shared verifier; its Verifier MUST be the canonical shell-quality check supplied by `livespec-dev-tooling` and wired into `just check`; and its Exemption MUST be an adjacent rationale for a noncanonical option profile plus any explicit accepted-finding declaration defined by the sibling-owned ShellCheck policy.

Co-edit every existing aggregate-form clause that the thin-Justfile rule changes: `### Enforcement-suite invocation`, `### Shared content sync — copier template`, `### Shared code sync — livespec-dev-tooling`, and `### Developer-tooling layout`. `just` MUST remain the single entry point, but the canonical ordered target inventory MUST move from the multiline `just check` recipe body into tracked static data, and the continue-on-failure loop MUST move into a shared executable runner supplied through the `livespec-dev-tooling` package. The one-line `just check` recipe MUST invoke that shared runner with the tracked inventory. The wiring-completeness invariant and in-repo gate MUST compare the tracked inventory with the canonical set; the template gate MUST project the canonical target set into a static inventory-data template and render only its one-line Justfile invocation; and the cross-repo backstop MUST inspect the same inventory. The shared runner MUST invoke every selected target sequentially through `just`, continue after a failure, and exit non-zero if any target failed. These co-edits MUST preserve the existing canonical-set derivation, alphabetical-order, consumer-private-tail, template-projection, and three-layer defense-in-depth requirements while removing every statement that locates the list or loop in a multiline recipe body. The copier channel MUST continue to carry only static scaffold and inventory data; the executable runner MUST be reused from the sibling package, preserving the existing static-vs-executable partition and reuse-by-default rule.

Co-edit `SPECIFICATION/contracts.md` section `wiring-completeness-cross-repo` so its local-clone and GitHub-fallback paths resolve the tracked static target inventory reached by the `just check` recipe and compare that inventory with the canonical set. It MUST NOT continue to infer canonical membership from the one-line recipe body.

Under the existing `## Scenarios` section, add Gherkin scenarios that pin the contributor-visible behavior without adding a new H2: (a) a dependency-only recipe and a one-line direct recipe using positional arguments are accepted when invoked from zsh and preserve arguments containing spaces; (b) a recipe containing a shebang body, multiline program, control operator, redirection, command substitution, chaining, or Just interpolation is rejected with a finding identifying the recipe; (c) a Bash or POSIX-sh file in the governed universe with its canonical initial option declaration passes, while a noncanonical declaration passes only with an adjacent rationale and otherwise fails; (d) an unpaired suspension, a status capture after restoration, or any unrelated command before capture or restoration fails, while a reasoned suspension that captures status immediately and then restores errexit passes; and (e) ShellCheck includes a tracked template script, analyzes it in the shebang-selected dialect, and rejects a newly introduced finding outside the sibling-owned acceptance policy. Each scenario MUST use Given/When/Then, MUST use the section's blank-line convention, and MUST link back to the new constraint clause.
