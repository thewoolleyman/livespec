## Proposal: Redesign spec-governance PR-merge policy around PR-introduced proposal stems

### Target specification files

- SPECIFICATION/spec.md
- SPECIFICATION/contracts.md
- SPECIFICATION/constraints.md
- SPECIFICATION/non-functional-requirements.md
- SPECIFICATION/scenarios.md
- tests/heading-coverage.json

### Summary

Add spec_governance.spec_pr_merge (safe default manual, opt-in auto-on-green, per-proposal spec_pr_merge_policy override) so a spec pull request can register for rebase-merge-on-green under an explicit, safely-resolvable policy — but, unlike the rejected v190 draft, specify HOW the CLI computes the required per-PR conservative fold (any ratified proposal floored to manual makes the whole PR manual) instead of leaving that plumbing unspecified.

### Motivation

Work-item livespec-bhammf preserves the two review blockers that sank the v190 predecessor (SPECIFICATION/history/v190/proposed_changes/spec-governance-pr-merge.md), rejected in v193's revise pass. Blocker 1: the v190 clause required the workflow to invoke `spec_governance.py --project-root "$GITHUB_WORKSPACE" --show-effective` to determine the per-PR conservative fold, but that invocation carries no identification of which ratified proposals the PR contains — after ratification each proposal's front matter (where spec_pr_merge_policy lives) sits in <spec-target>/history/vNNN/proposed_changes/<stem>.md, the PR-head checkout also contains every historical cut's front matter, and proposed_changes/ may hold unrelated pending proposals, so no scan of project-root state alone can identify "the proposals this PR contains" — only the PR's merge-base diff can. Taken literally the clause returns the GLOBAL effective value, silently auto-merging a change its own author floored to manual: the exact inversion the fold exists to prevent. This proposal fixes that by specifying the derivation (git merge-base diff, computed by the WORKFLOW, not the CLI) and the transport (repeatable --proposal-stem <stem> CLI arguments) explicitly, and defines a --pr-effective-policy flag so an explicitly-empty derived stem set is distinguishable from "no fold requested" and resolves to manual rather than silently falling back to the global value. Blocker 2 (clause-lockstep miss on the scenarios.md counting preamble) is VERIFIED ALREADY MOOT: the live scenarios.md preamble no longer states a literal error-path count (git history shows it was generalized to 'policy and wrapper error paths' wording during Increment 1's own heading additions, before this proposal); this proposal therefore adds the new heading without touching the preamble, and states this verification explicitly so the ratifying reviewer does not need to re-derive it from scratch.

REDRAFT NOTE (round 2): an independent adversarial review of the first filing returned BLOCKERS FOUND (4), all verified against live `origin/master` bytes and fixed below without disturbing anything the review confirmed (the derivation + transport design, the conservative fold emitted alongside the global value, empty/underivable never falling back to the global value, the front-matter topic matching the stem, the single new H2 with its integration-tier-keyworded heading-coverage co-edit, and cross-repo consistency verified against eight sibling repos' spec trees — a mixed-role set spanning dev-tooling, orchestrator plugins, Drivers, runtime, overseer, and console, NOT eight orchestrator plugins). The review also corrected an earlier, separately-issued claim that scenarios.md's preamble still carried a literal error-path count requiring re-derivation — that claim was wrong; the "VERIFIED ALREADY MOOT" note above was correct and the preamble is untouched, unchanged from the first filing.

THIRD FILING NOTE (round 3): a second independent adversarial review re-derived all four round-1 closures (achieved by the round-2 redraft) at the new SHA and confirmed all four held; it found two NEW blockers introduced by the round-2 redraft, both fixed below without touching the confirmed-correct round-1 closures. New Blocker A: the round-2 text directed an "amendment" to a non-existent `auto-enable-merge.yml` clause inside §"Workflow discipline — spec-side changes" (that clause lives under the different section §"Shared content sync — copier template", line 442, and §"Workflow discipline" contains zero `auto-enable-merge` occurrences) and separately directed a direct edit to CI workflow YAML/Jinja files, which a revise has no sanctioned mechanism to make. Fixed by recasting both as one ADDED spec requirement (never an amend directive) in an explicitly named new subsection, with the actual workflow-file implementation correctly routed to a separate, out-of-band work-item rather than this proposal's `resulting_files[]`. New Blocker B: the round-2 text asserted the mechanism becomes uniform across "its eight orchestrator-plugin siblings" — both the count and the category were wrong (the fleet manifest names exactly TWO `livespec-orchestrator-*` repos); fixed by dropping the hardcoded count everywhere it appeared, including in this note's own round-2 paragraph above. One hardening was also added (never optional per this filing): a PR-diff derivation that disagrees between the hosting API's file listing and a local-git computation, or that computes an entirely-empty PR diff, now counts as derivation FAILURE rather than silently landing in the known-empty, unfolded path.

FOURTH FILING NOTE (round 4): a third independent adversarial review confirmed New Blockers A and B (round 3) both CLOSED — the workflow-file separation, the derived repo-set form, the hardening's placement in `spec.md` `effective_spec_pr_merge`(b), and the payload-vs-commentary bracketing all held; none of it is touched here. It found ONE new, purely positional blocker: the round-3 directive placed the new `auto-enable-merge` subsection as a SIBLING `###` heading immediately after §"Workflow discipline — spec-side changes" step 6, but that section is itself `###`, so a same-level heading there does not nest under it — it silently re-parents everything between step 6 and the section's actual end (including the load-bearing Primary-checkout commit-refuse hook rule) out from under a section FOUR live cross-references (three in `non-functional-requirements.md`, one in `contracts.md`) still name explicitly. Also: the hardening from round 3 is TIGHTENED from an either/or derivation to a mandatory dual-source agreement requirement, with its honest limit stated explicitly rather than overclaimed; three more expiring-wording/dangling-reference fixes are folded in; and the round-3 note's "round-2 closures" mislabel (corrected above) is fixed.

### Proposed Changes

SPECIFICATION/spec.md — under `### Spec-governance policy settings`, add a NINTH registry row (the live table already carries eight rows: propose_change_mode, critique_mode, in_flight_alignment, doctor_dispositions, revise_decision_mode, drift_acceptance_mode, ratification_review, ratification_reviewer_model): `spec_pr_merge` | `manual | auto-on-green` | safe default `manual` | per-proposal override `spec_pr_merge_policy`. Add a new resolution paragraph `effective_spec_pr_merge`, after the `effective_ratification_review` paragraph, specifying TWO resolutions the CLI exposes.

(a) Single-proposal effective policy: for one proposal identified by its stem, resolve in order — a present valid `spec_pr_merge_policy` front-matter value on that proposal's file; else the valid global `spec_governance.spec_pr_merge` value; else the safe default `manual`. A present malformed, wrong-typed, or unknown `spec_pr_merge_policy` value, and missing or malformed global policy, MUST resolve to `manual` without raising. A stem that matches ZERO files under `<spec-root>/history/*/proposed_changes/<stem>.md` resolves to `manual` for that stem (fail-safe). A stem that matches MORE THAN ONE file — the glob is not injective: a stem can recur verbatim across separate history cuts (e.g. a proposal re-filed and re-ratified under the same slug after an earlier rejection or supersession) — resolves via the SAME conservative fold as (b): `manual` if ANY matching file's policy resolves `manual`, `auto-on-green` only if EVERY matching file resolves `auto-on-green`. State both the zero-match and multi-match rules together, immediately adjacent, so neither non-happy case is left implicit.

(b) Pull-request effective policy (the conservative fold): given the explicit, NON-EMPTY set of ratified proposal stems a pull request introduces — supplied by the CALLER, never derived by this CLI itself — the pull-request effective policy is `auto-on-green` only when every stem's single-proposal effective policy (per (a)) resolves to `auto-on-green`; any stem resolving to `manual` makes the pull-request effective policy `manual`. An EMPTY stem set passed to this resolution explicitly (the CLI's `--pr-effective-policy` invoked with zero `--proposal-stem` values) resolves to `manual` as the CLI's own fail-safe floor, never falling back to the global effective value. State explicitly, however, that (b) is defined to GOVERN only a pull request that ratifies one or more proposals: deriving whether a pull request ratifies any proposal at all, and if so which stems, is the WORKFLOW's responsibility, specified in `non-functional-requirements.md` §"Spec pull-request auto-merge requirement" (a cross-file reference, since that workflow-facing requirement is not defined in this file), computed from the pull request's merge-base diff against the non-`-revision` files it ADDS under `<spec-root>/history/*/proposed_changes/` across EVERY configured spec root (the main spec plus any `<spec-root>/templates/<name>/` sub-specs). A workflow that successfully computes this diff and finds ZERO added stems has determined the pull request ratifies NOTHING; such a pull request is NOT subject to `spec_pr_merge` at all — it is not "an empty stem set passed to the fold", it is "no fold invocation", and its eligibility is decided entirely by the registration-time hard floors and non-spec eligibility gates defined in contracts.md, unaffected by this key. A workflow whose diff computation itself FAILS (git or hosting-API error, not merely zero matches) cannot distinguish "ratifies nothing" from "ratifies something unknown", and MUST treat the pull request as ineligible for auto-merge registration exactly as an effective-`manual` policy would — this is the sole fail-safe/fail-closed case; a successfully-computed empty set is not it. HARDENING (required, not optional): the workflow MUST compute BOTH the hosting-API's pull-request file listing AND a local-git derivation, and the two MUST AGREE; the workflow MUST treat a disagreement between the two derivations, OR an entirely-empty computed pull-request diff (zero changed files total — not merely zero matched proposed-change stems — which is impossible for a genuine pull request and therefore a safe, costless signal of a broken or mis-scoped diff computation), as derivation FAILURE, resolving to `manual`. STATE THE LIMIT HONESTLY rather than overclaiming: this closes the SOURCE-level failure class — a wrong base ref, a shallow-checkout artifact, or API/git divergence — where the two derivations disagree or one is simply broken. It does NOT close a FILTER-level bug: if the identical faulty pathspec or scoping error is applied to BOTH derivations, both agree and both are wrong, and a pull request that genuinely introduces a `manual`-floored proposal could still yield a false KNOWN-EMPTY. That residual is an implementation-correctness concern for the eventual workflow implementation, not a specification-drafting gap this proposal can close by wording alone.

SPECIFICATION/contracts.md — under `### Spec-governance input envelopes`, add a paragraph parallel to the existing `decision_policy` paragraph: a proposed-change file MAY carry `spec_pr_merge_policy: manual | auto-on-green` in YAML front matter, applying to that file only, with precedence over the global `spec_governance.spec_pr_merge` value; an absent field inherits the valid global value; a present malformed, wrong-typed, or unknown field resolves to `manual` without raising.

Under `### Spec-governance control wrapper`, extend `--project-root <path> --show-effective` with two additive, optional arguments that do not change its existing zero-argument behavior: repeatable `--proposal-stem <stem>` and boolean `--pr-effective-policy`. Passing `--pr-effective-policy` (with zero or more `--proposal-stem` values) additionally emits, alongside the existing global effective value, the pull-request effective policy computed as `effective_spec_pr_merge`(b) above; omitting `--pr-effective-policy` preserves the current global-only output exactly. `--proposal-stem` supplied WITHOUT `--pr-effective-policy` is a usage error: the CLI MUST reject it and exit 2 via `IOFailure(UsageError)`, mirroring the existing `--skip-pre-check`/`--run-pre-check` mutually-exclusive-argument convention — a stem list with no fold requested is a caller mistake, not a case worth silently ignoring. Add to the action grammar list: `set-spec-pr-merge:global:<manual-or-auto-on-green-or-clear>` and `set-spec-pr-merge:proposal:<proposal-stem>:<manual-or-auto-on-green-or-clear>`, following the `clear`/validation/atomic-replacement/no-lifecycle-mutation rules already stated for the surrounding actions. Extend the journal paragraph: an auto-on-green registration attempt MUST append an event naming `spec_pr_merge`, the pull-request identity, the derived proposal-stem set, the resolved pull-request effective policy and its source, registration result, required-gate state, and final merge evidence when available, following the existing digest-only/no-raw-content discipline; journal failure requires human input and prevents registration.

Add a new subsection, `### Spec pull-request merge-registration mechanics`, DEFINING NORMATIVELY (not referencing as already-ratified) the floors and gates `effective_spec_pr_merge` and the auto-merge requirement below depend on. [DIRECTIVE COMMENTARY FOR THE RATIFIER — do NOT copy this bracketed sentence into contracts.md, it is guidance about why the subsection must define rather than reference: these floors/gates were previously described only in the REJECTED v190 draft and are not yet spec-defined anywhere on `origin/master` as of this filing, which is why they need a normative home now rather than a citation to something already ratified.] The subsection's ratified body (this part IS payload):

- Registration-time hard floors (ALL MUST hold before an `auto-on-green` pull request registers for merge-when-green): the spec change has been ratified through revise; an open non-draft pull request targets the governed default branch; the pull-request author satisfies the workflow's configured human/release-App identity allowlist; no `do-not-merge` label is present; no unresolved GitHub changes-requested review exists at registration time; the repository permits rebase merge; and the spec-governance policy journal is writable.
- Completion-time host guarantees (owned by branch protection / host merge-queue semantics AFTER registration, never by this policy): the required all-green status check MUST succeed before merge; the policy MUST NOT bypass, weaken, relabel, or replace a required status check; MUST NOT use squash or merge-commit mode; MUST NOT merge a red pull request. A hosting service that cannot provide merge-when-green semantics MUST require human input instead of polling and force-merging.
- Non-spec eligibility gates (the gates every pull request — spec-touching or not — passes through, independent of `spec_pr_merge`): draft state, `do-not-merge` label, human-author allowlist, and the release-please App exception on a `release-please--` branch. `spec_pr_merge` governs ONLY whether a ratifying spec pull request additionally clears the conservative fold; it neither replaces nor loosens these gates.

Add an exported predicate, `awaits_manual_spec_pr_merge`, true exactly when the pull-request effective policy is `manual` or a registration-time hard floor prevents registration, false once an eligible pull request is validly registered for merge-when-green even while CI is pending or red; any awareness/advertisement surface MUST consume this predicate rather than re-derive it, and core does not normatively name or own an orchestrator awareness surface for it.

SPECIFICATION/constraints.md — in the paragraph enumerating safe-default resolution for spec-governance keys (the one stating, in its live wording, "revise decisions inherit manual confirmation" — quoted verbatim from `origin/master`, not the `revise_decision_mode` literal used in an earlier draft of this proposal), add `spec_pr_merge` to that enumeration: missing or malformed policy resolves to `manual`; an explicitly-empty proposal-stem set passed to the pull-request-level fold resolves to `manual`, never to the unfolded global value; a diff-derivation failure (the workflow cannot determine whether the pull request ratifies anything) MUST be treated as ineligible for registration, distinct from a successfully-computed zero-stem result which is simply outside this key's governance. State that the stem-set derivation is a workflow (caller) responsibility, never performed by the deterministic control CLI, and that a policy edit under this key is never itself the merge-registration or CI-bypass action it configures — mirroring the existing rule for the other spec-governance keys in this file. Add a normative sentence for unsupported hosting: a hosting service that cannot provide merge-when-green semantics MUST require human input instead of polling and force-merging (cross-referencing `contracts.md` §"Spec pull-request merge-registration mechanics" as the fuller statement).

The new subsection's normative body (payload — this text belongs in `non-functional-requirements.md`): both `livespec`'s root-repo `.github/workflows/auto-enable-merge.yml` AND the orchestrator-plugin copier template's `templates/orchestrator-plugin/.github/workflows/auto-enable-merge.yml.jinja` MUST implement the following requirement for a pull request whose diff touches a configured spec root: compute the merge-base diff, derive the added non-`-revision` proposed-change stems under `<spec-root>/history/*/proposed_changes/` across every configured spec root, and — ONLY when that derived set is non-empty — invoke `spec_governance.py --project-root "$GITHUB_WORKSPACE" --show-effective --pr-effective-policy --proposal-stem <stem>` (repeated once per derived stem) to obtain the pull-request effective policy, registering auto-merge only on an `auto-on-green` result. A pull request touching no spec root, or whose derived stem set is successfully computed as EMPTY (ratifies nothing), MUST fall through unchanged to the non-spec eligibility gates defined in `contracts.md` §"Spec pull-request merge-registration mechanics" — the same path as a non-spec pull request. A pull request whose diff-derivation step FAILS (per spec.md's `effective_spec_pr_merge`(b) failure definition, including the hardening rule there) MUST NOT register for auto-merge. This requirement applies uniformly to `livespec` itself and to every `livespec-orchestrator-*` sibling generated from the template — DERIVE the applicable-repo set from template consumption, never a hardcoded count or category. Repo `thewoolleyman/livespec` MAY declare `spec_governance.spec_pr_merge: auto-on-green` once this contract ships; other repos inherit safe `manual` when absent.

Separately, ADD a one-line note immediately after the EXISTING bullet at `non-functional-requirements.md`'s line 442 (under §"Shared content sync — copier template"), leaving that bullet's own text byte-for-byte UNCHANGED: because a plain propose-change-filing pull request (one that adds a file under `proposed_changes/` but nothing under `history/*/proposed_changes/`) always derives a successfully-computed, KNOWN-EMPTY stem set, it is NOT subject to the conservative fold and keeps its existing, unaffected auto-merge-on-open eligibility — so the new §"Spec pull-request auto-merge requirement" does not weaken the incident-driven cadence guarantee that bullet documents. Only a pull request that actually RATIFIES one or more proposals (i.e., its diff adds files under `history/*/proposed_changes/`) is gated by `spec_pr_merge`.
