## Proposal: Redesign spec-governance PR-merge policy around PR-introduced proposal stems

### Target specification files

- SPECIFICATION/spec.md
- SPECIFICATION/contracts.md
- SPECIFICATION/constraints.md
- SPECIFICATION/non-functional-requirements.md
- SPECIFICATION/scenarios.md
- tests/heading-coverage.json

### Summary

Add spec_governance.spec_pr_merge (safe default manual, opt-in auto-on-green, per-proposal spec_pr_merge_policy override) so a spec pull request can register for rebase-merge-on-green under an explicit, safely-resolvable policy — but, unlike the rejected v190 draft, specify HOW the CLI computes the required per-PR conservative fold (any ratified proposal floored to manual makes the whole PR manual) instead of leaving that plumbing unspecified.

### Motivation

Work-item livespec-bhammf preserves the two review blockers that sank the v190 predecessor (SPECIFICATION/history/v190/proposed_changes/spec-governance-pr-merge.md), rejected in v193's revise pass. Blocker 1: the v190 clause required the workflow to invoke `spec_governance.py --project-root "$GITHUB_WORKSPACE" --show-effective` to determine the per-PR conservative fold, but that invocation carries no identification of which ratified proposals the PR contains — after ratification each proposal's front matter (where spec_pr_merge_policy lives) sits in <spec-target>/history/vNNN/proposed_changes/<stem>.md, the PR-head checkout also contains every historical cut's front matter, and proposed_changes/ may hold unrelated pending proposals, so no scan of project-root state alone can identify "the proposals this PR contains" — only the PR's merge-base diff can. Taken literally the clause returns the GLOBAL effective value, silently auto-merging a change its own author floored to manual: the exact inversion the fold exists to prevent. This proposal fixes that by specifying the derivation (git merge-base diff, computed by the WORKFLOW, not the CLI) and the transport (repeatable --proposal-stem <stem> CLI arguments) explicitly, and defines a --pr-effective-policy flag so an explicitly-empty derived stem set is distinguishable from "no fold requested" and resolves to manual rather than silently falling back to the global value. Blocker 2 (clause-lockstep miss on the scenarios.md counting preamble) is VERIFIED ALREADY MOOT: the live scenarios.md preamble no longer states a literal error-path count (git history shows it was generalized to 'policy and wrapper error paths' wording during Increment 1's own heading additions, before this proposal); this proposal therefore adds the new heading without touching the preamble, and states this verification explicitly so the ratifying reviewer does not need to re-derive it from scratch.

### Proposed Changes

SPECIFICATION/spec.md — under `### Spec-governance policy settings`, add an eighth registry row: `spec_pr_merge` | `manual | auto-on-green` | safe default `manual` | per-proposal override `spec_pr_merge_policy`. Add a new resolution paragraph `effective_spec_pr_merge`, after the `effective_ratification_review` paragraph, specifying TWO resolutions the CLI exposes. (a) Single-proposal effective policy: for one proposal identified by its stem, resolve in order — a present valid `spec_pr_merge_policy` front-matter value on that proposal's file; else the valid global `spec_governance.spec_pr_merge` value; else the safe default `manual`. A present malformed, wrong-typed, or unknown `spec_pr_merge_policy` value, and missing or malformed global policy, MUST resolve to `manual` without raising. A stem that cannot be located under `<spec-root>/history/*/proposed_changes/<stem>.md` resolves to `manual` for that stem (fail-safe). (b) Pull-request effective policy (the conservative fold): given the explicit set of ratified proposal stems a pull request introduces — supplied by the CALLER, never derived by this CLI itself — the pull-request effective policy is `auto-on-green` only when that set is non-empty AND every stem's single-proposal effective policy (per (a)) resolves to `auto-on-green`; an EMPTY stem set, or any stem resolving to `manual`, makes the pull-request effective policy `manual`. State explicitly that deriving the stem set is the WORKFLOW's responsibility, computed from the pull request's merge-base diff against the non-`-revision` files it ADDS under `<spec-root>/history/*/proposed_changes/`; the CLI only folds over the set it is given, never inspecting git state itself, so an empty or underivable set passed explicitly resolves to `manual` rather than silently falling back to the global effective value — fail safe, never fail open.

SPECIFICATION/contracts.md — under `### Spec-governance input envelopes`, add a paragraph parallel to the existing `decision_policy` paragraph: a proposed-change file MAY carry `spec_pr_merge_policy: manual | auto-on-green` in YAML front matter, applying to that file only, with precedence over the global `spec_governance.spec_pr_merge` value; an absent field inherits the valid global value; a present malformed, wrong-typed, or unknown field resolves to `manual` without raising. Under `### Spec-governance control wrapper`, extend `--project-root <path> --show-effective` with two additive, optional arguments that do not change its existing zero-argument behavior: repeatable `--proposal-stem <stem>` and boolean `--pr-effective-policy`. Passing `--pr-effective-policy` (with zero or more `--proposal-stem` values) additionally emits, alongside the existing global effective value, the pull-request effective policy computed as `effective_spec_pr_merge`(b) above; omitting `--pr-effective-policy` preserves the current global-only output exactly. Add to the action grammar list: `set-spec-pr-merge:global:<manual-or-auto-on-green-or-clear>` and `set-spec-pr-merge:proposal:<proposal-stem>:<manual-or-auto-on-green-or-clear>`, following the existing `clear`/validation/atomic-replacement/no-lifecycle-mutation rules stated for the surrounding actions. Extend the journal paragraph: an auto-on-green registration attempt MUST append an event naming `spec_pr_merge`, the pull-request identity, the derived proposal-stem set, the resolved pull-request effective policy and its source, registration result, required-gate state, and final merge evidence when available, following the existing digest-only/no-raw-content discipline; journal failure requires human input and prevents registration. Add an exported predicate, `awaits_manual_spec_pr_merge`, true exactly when the pull-request effective policy is `manual` or a registration-time hard floor prevents registration, false once an eligible pull request is validly registered for merge-when-green even while CI is pending or red; any awareness/advertisement surface MUST consume this predicate rather than re-derive it, and core does not normatively name or own an orchestrator awareness surface for it.

SPECIFICATION/constraints.md — in the paragraph enumerating safe-default resolution for spec-governance keys (the one already stating '`revise_decision_mode` inherit manual confirmation' etc.), add `spec_pr_merge` to that enumeration: missing or malformed policy resolves to `manual`; the pull-request-level fold additionally treats an empty or underivable proposal-stem set as `manual`, never as an unfolded global value. State that the stem-set derivation is a workflow (caller) responsibility, never performed by the deterministic control CLI, and that a policy edit under this key is never itself the merge-registration or CI-bypass action it configures — mirroring the existing rule for the other spec-governance keys in this file.

SPECIFICATION/non-functional-requirements.md — under `### Workflow discipline — spec-side changes`, amend step 5 so it branches on the pull-request effective `spec_pr_merge` policy: an effective `manual` policy leaves the pull request for human rebase-merge exactly as today; an effective `auto-on-green` policy registers rebase auto-merge (equivalent to `gh pr merge --rebase --auto`) after opening and before CI completes, subject to the existing registration-time hard floors (ratified, open non-draft PR, author allowlist, no `do-not-merge` label, no unresolved changes-requested review, rebase-merge permitted, journal writable). Co-amend step 6 so worktree/branch cleanup occurs after CONFIRMED merge under either policy, without assuming a manual `gh pr merge --delete-branch` invocation in the automatic path. Amend the `auto-enable-merge.yml` requirement: for a pull request whose diff touches a configured spec root, the workflow MUST compute its merge-base diff, derive the added non-`-revision` proposed-change stems under `<spec-root>/history/*/proposed_changes/`, and invoke `spec_governance.py --project-root "$GITHUB_WORKSPACE" --show-effective --pr-effective-policy --proposal-stem <stem>` (repeated once per derived stem, zero or more times) to obtain the pull-request effective policy; it registers auto-merge only on an `auto-on-green` result. A pull request touching NO spec root, or whose diff-derivation step itself fails, MUST fall back to the existing non-spec eligibility gates and MUST NOT be treated as auto-on-green by default. Non-spec pull requests retain every existing eligibility gate (draft state, `do-not-merge` label, human-author allowlist, release-please App exception) unchanged. Repo `thewoolleyman/livespec` MAY declare `spec_governance.spec_pr_merge: auto-on-green` once this contract ships; other repos inherit safe `manual` when absent.

SPECIFICATION/scenarios.md — extend `## Happy-path revise` with three legs: a global `auto-on-green` setting registering merge-on-green for a single-proposal PR; a per-proposal `manual` override defeating a global `auto-on-green` setting; and a multi-proposal PR where one proposal's `manual` override conservatively folds the whole PR to `manual` even though every other included proposal resolves `auto-on-green`. Add a new heading `## Error path — spec pull request cannot auto-merge` covering: a red required gate blocking completion; a draft, `do-not-merge` label, or unresolved changes-requested review blocking registration; an invalid or malformed policy value resolving to `manual`; an empty or underivable derived proposal-stem set resolving the pull-request fold to `manual` rather than the global value; unsupported hosting requiring human input instead of polling and force-merging; journal-append failure preventing registration; and default configuration (no `spec_pr_merge` set anywhere) arming no unattended merge. Do NOT edit the file's introductory preamble sentence — it already reads generically ('policy and wrapper error paths') with no literal error-path count to re-derive; this was verified against live `git log -p` history before filing, so the ratifying reviewer need not re-check it.

tests/heading-coverage.json — add a `TODO` entry for the new `## Error path — spec pull request cannot auto-merge` scenarios.md heading, in the SAME resulting_files[] payload as the scenarios.md edit at ratification time, following the existing sibling entries' shape exactly: `spec_root: SPECIFICATION`, `spec_file: scenarios.md`, `test: TODO`, a `reason` whose wording explicitly names the INTEGRATION TIER (matching one of the keywords `tier`, `integration`, or `e2e`, per check-heading-coverage direction 4 — a reason citing only the owning work-item fails that check even when complete and accurate), and `work_item: livespec-jvdvx4` (the open parent epic, matching the convention the three sibling Increment-1 TODO entries and the Increment-3 'Drift acceptance under each mode' entry already use for follow-up integration-tier coverage owned by the epic rather than a since-closed slice).
