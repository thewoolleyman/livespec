## Proposal: Promote pi from recognized future Driver target to current reference Driver work

### Target specification files

- SPECIFICATION/spec.md

### Summary

spec.md's Reference Driver bindings paragraph counts two current reference Driver repositories and parks Pi (with OpenCode) as a recognized future target; the distribution sentence says core is distributed to BOTH supported agent runtimes via marketplace catalogs. With livespec-driver-pi entering reference work, the count moves to three, pi moves out of the future-targets parenthetical, and the distribution sentence widens to name the pi channel — which is a direct git-package install rather than a third catalog file.

### Motivation

The bootstrap-pi-driver plan (plan/bootstrap-pi-driver/, epic livespec-g5h5ff) creates livespec-driver-pi as a full driver-plugin fleet member. spec.md §"Contract + reference implementations architecture" already admits Pi as a future Driver target, so this is the planned promotion, not a new direction. Leaving the two-Driver count and the BOTH-runtimes distribution sentence unamended would create exactly the clause-lockstep rot .ai/spec-proposal-review.md warns about.

### Proposed Changes

In `SPECIFICATION/spec.md` §"Contract + reference implementations architecture", the **Reference Driver bindings** paragraph currently reads verbatim: "**Reference Driver bindings.** Two per-runtime Driver plugin repositories are current reference work, each shipping THIN agent-runtime SKILL.md bindings over CORE's prose and wrapper CLIs and adding no operation behavior of its own: `livespec-driver-claude` (Claude Code) and `livespec-driver-codex` (OpenAI Codex CLI/TUI). Both expose the same eight spec-side operations; each resolves CORE's plugin root at runtime, reads the named core prose, and invokes the config-named spec-side CLI. Other runtimes (OpenCode, Pi) are recognized future Driver targets the contract admits, not commitments." It MUST be replaced with: "**Reference Driver bindings.** Three per-runtime Driver plugin repositories are current reference work, each shipping THIN agent-runtime SKILL.md bindings over CORE's prose and wrapper CLIs and adding no operation behavior of its own: `livespec-driver-claude` (Claude Code), `livespec-driver-codex` (OpenAI Codex CLI/TUI), and `livespec-driver-pi` (the pi coding agent). All expose the same eight spec-side operations; each resolves CORE's plugin root at runtime, reads the named core prose, and invokes the config-named spec-side CLI. OpenCode remains a recognized future Driver target the contract admits, not a commitment." Separately, the distribution sentence that currently reads verbatim: "The core artifact is distributed to BOTH supported agent runtimes via marketplace catalogs declared at the repo root: a Claude Code marketplace at `.claude-plugin/marketplace.json` and a Codex marketplace at `.agents/plugins/marketplace.json` (with a paired `.codex-plugin/plugin.json`), both carrying the SAME `prose/` and `scripts/` over which each runtime's Driver plugin binds. See `contracts.md` §"Plugin distribution" for both core install paths and for how each runtime's Driver plugin (`livespec-driver-claude`, `livespec-driver-codex`) supplies its interactive command surface." MUST be replaced with: "The core artifact is distributed to every supported agent runtime from the same repo-root packaging: a Claude Code marketplace at `.claude-plugin/marketplace.json`, a Codex marketplace at `.agents/plugins/marketplace.json` (with a paired `.codex-plugin/plugin.json`), and — for the pi coding agent — a direct git-package install of the repository itself, all carrying the SAME `prose/` and `scripts/` over which each runtime's Driver plugin binds. See `contracts.md` §"Plugin distribution" for the core install paths and for how each runtime's Driver plugin (`livespec-driver-claude`, `livespec-driver-codex`, `livespec-driver-pi`) supplies its interactive command surface." Additionally, in the **Terminology guard** paragraph of §"Workflow planes and the Planning Lane", the parenthetical in the sentence that currently reads verbatim: "\"Driver\" already names the per-agent-runtime binding (`livespec-driver-claude`, `livespec-driver-codex`) that binds core's spec-side CLIs and prose to ONE tool runtime" MUST be widened to "(`livespec-driver-claude`, `livespec-driver-codex`, `livespec-driver-pi`)" so the Driver enumeration there stays in lockstep with the Reference Driver bindings paragraph.

## Proposal: Plugin distribution: the pi channel — core as a resource-less pi git package, project-scoped enablement, release-branch currency

### Target specification files

- SPECIFICATION/contracts.md

### Summary

Adds the pi distribution contract to contracts.md §"Plugin distribution" as a sibling of the existing Codex paragraph: core is consumed by pi as a resource-less git package (no pi manifest, no resource directories — the artifact-carrier role stated by contract rather than left incidental), installed project-scoped via a committed .pi/settings.json at the @release branch ref, refreshed by `pi update --extensions`, gated by pi's project-trust mechanism for non-interactive runs; and amends the Driver-surface enumeration paragraph to name the pi Driver and its /skill:livespec-<op> command surface.

### Motivation

The bootstrap-pi-driver plan requires a ratified distribution contract before the livespec-driver-pi bindings land. Research (plan/bootstrap-pi-driver/research/pi-extension-surface.md, including its closed open item 2) establishes on pi v0.84.1: a git-installed pi package with no resource directories loads zero resources without error; `pi install <source> -l` writes a committed .pi/settings.json that pi auto-installs from on startup after project trust; and — by two independent derivations, a live scratch-project observation and a read of pi's shipped package-manager source — a branch name is a valid git ref and `pi update --extensions` moves the clone to the fetched ref tip (a hard reset to FETCH_HEAD, not a merge). Note pi's published documentation describes git refs as pinned tags or commits that updates do not move; the observed branch-ref behavior contradicts that doc text, which is why the research record carries the source derivation and why the contract sentence below anchors the observed version.

### Proposed Changes

In `SPECIFICATION/contracts.md` §"Plugin distribution", immediately after the existing Codex distribution paragraph (the paragraph beginning "`livespec` is ALSO distributed as a Codex plugin:"), a new paragraph MUST be added: "`livespec` is ALSO distributed to the pi coding agent, as a **resource-less pi git package**: a consumer installs core with `pi install git:github.com/thewoolleyman/livespec@release -l`, which records the package in the project's committed `.pi/settings.json` and clones the repository to `.pi/git/github.com/thewoolleyman/livespec/` (project scope) or `~/.pi/agent/git/github.com/thewoolleyman/livespec/` (user scope). Core intentionally declares NO `pi` manifest key and ships NO pi conventional resource directories (`extensions/`, `skills/`, `prompts/`, `themes/` at the repo root), so pi loads ZERO resources from the core package — this is the same artifact-carrier role core plays on the Claude path, stated here by contract so it is a commitment rather than an accident of layout; the pi Driver resolves core's `prose/` and `scripts/` under `.claude-plugin/` inside that clone. The install ref MUST be the `release` branch (the same moving release channel the Claude and Codex marketplaces track via `ref: release`); `pi update --extensions` is the currency-refresh verb — verified on pi v0.84.1 to move a branch-ref clone to the fetched branch tip, a behavior pi's own documentation does not promise for git refs (it describes them as pinned tags or commits), so this clause MUST be re-verified against pi's package manager on any pi major-version bump — and pi's startup auto-install of missing project packages covers the missing-but-declared case after the project is trusted. pi plugin enablement is PROJECT-SCOPED like the Claude path (a committed `.pi/settings.json`, unlike Codex's host-wide `~/.codex/config.toml`), with one pi-specific caveat that is part of this contract: pi's project-trust gate means a NON-INTERACTIVE pi invocation (`-p`, `--mode json`, `--mode rpc`) silently ignores project-local settings and packages unless a trust decision is pre-seeded (`~/.pi/agent/trust.json`, a global `defaultProjectTrust: always`, or a per-run `--approve`), so any unattended pi drive of a `/livespec:*` operation MUST ensure trust is established or the operation resolves nothing. Installation MUST NOT be verified by the settings entry alone; the verification is the acceptance bar in `non-functional-requirements.md` §"pi dogfooding constraints"." Additionally, the Driver-surface enumeration paragraph that currently reads verbatim: "After installing core plus a runtime Driver, the Driver exposes the same eight operations as that runtime's interactive command surface: `seed`, `propose-change`, `critique`, `revise`, `doctor`, `prune-history`, `help`, `next`. The Claude Code Driver exposes them as `/livespec:*` slash commands namespaced under the Driver plugin name; the Codex Driver (`livespec-driver-codex`) exposes the same eight via Codex plugin skills resolving the same operations. Renaming any operation's command surface requires a propose-change cycle. The command surface is Driver-owned runtime mechanics; core supplies the harness-neutral prose, wrapper CLIs, templates, and schemas that each Driver binds." MUST have its second sentence replaced so the paragraph reads: "After installing core plus a runtime Driver, the Driver exposes the same eight operations as that runtime's interactive command surface: `seed`, `propose-change`, `critique`, `revise`, `doctor`, `prune-history`, `help`, `next`. The Claude Code Driver exposes them as `/livespec:*` slash commands namespaced under the Driver plugin name; the Codex Driver (`livespec-driver-codex`) exposes the same eight via Codex plugin skills resolving the same operations; the pi Driver (`livespec-driver-pi`) exposes the same eight as pi skills named `livespec-<operation>` (invoked as `/skill:livespec-<operation>` interactively, and by the same skill-command form in non-interactive `pi -p` / RPC prompts — pi skill names admit no colon-namespacing, so the `livespec-` name prefix carries the namespace). Renaming any operation's command surface requires a propose-change cycle. The command surface is Driver-owned runtime mechanics; core supplies the harness-neutral prose, wrapper CLIs, templates, and schemas that each Driver binds."

## Proposal: Driver-shipped hooks: generalize the two-Driver clauses to every Driver, require the pi footgun guard, and record pi's memory-store non-requirement

### Target specification files

- SPECIFICATION/contracts.md

### Summary

The Driver-shipped hooks section binds the no-shadow-ledger hook and the auto-memory guards with BOTH-Drivers phrasing that silently rots when a third Driver exists. This finding generalizes those clauses to every-Driver form, adds the pi footgun-guard requirement (a pi extension blocking forbidden tool calls via pi's tool_call event, gating the mutating operations exactly as the Codex guard does), and records by contract that the pi Driver requires NO auto-memory guard sibling because pi has no local-memory store.

### Motivation

Clause-lockstep repair required by the livespec-driver-pi bootstrap (plan bootstrap-pi-driver, epic livespec-g5h5ff): .ai/spec-proposal-review.md names counts-and-enumerations rot as a ratifies-cleanly-then-rots defect class, and the hooks section carries three such BOTH-Driver phrasings. The pi footgun guard is implementable: pi extensions receive a tool_call event whose handler can return a block decision (verified in the installed pi v0.84.1 documentation).

### Proposed Changes

In `SPECIFICATION/contracts.md` §"Driver-shipped hooks": (1) The sentence fragment that currently ends with the words "so its one neutral body can ship byte-identically in both Drivers' bundles" (the fragment beginning "the cross-Driver no-shadow-ledger hook is a Python script invoked as", in the paragraph opening §"Driver-shipped hooks"; the invocation form quoted there, backtick-wrapped with plain double quotes around the `${CLAUDE_PLUGIN_ROOT}` path, is retained unchanged) MUST be amended to end "...so its one neutral body can ship byte-identically in every Driver's bundle". (2) The sentence that currently reads verbatim "Unlike the plan-persistence WARN hook, which the Claude bundle carries alone, the no-shadow-ledger hook is REQUIRED in BOTH Drivers' bundles (see the cross-Driver single-sourcing paragraph below); the auto-memory-write guard is likewise present in BOTH bundles, but as a PER-RUNTIME pair rather than a single shared body — the Claude auto-memory redirect targets the Claude layout (`~/.claude/.../memory/*.md`), and the Codex Driver ships its own guard targeting the Codex local-memory store (`~/.codex/memories/`), per the Codex auto-memory-write-guard paragraph below." MUST be replaced with: "Unlike the plan-persistence WARN hook, which the Claude bundle carries alone, the no-shadow-ledger hook is REQUIRED in EVERY Driver's bundle (see the cross-Driver single-sourcing paragraph below); the auto-memory-write guard is likewise required PER RUNTIME rather than as a single shared body — but only in a Driver whose runtime HAS a harness-private local-memory store: the Claude auto-memory redirect targets the Claude layout (`~/.claude/.../memory/*.md`), the Codex Driver ships its own guard targeting the Codex local-memory store (`~/.codex/memories/`) per the Codex auto-memory-write-guard paragraph below, and the pi Driver ships NONE because pi has no local-memory store (an absence observed in pi v0.84.1 — anchored because it is a claim about an external project no gate here watches) — if a future pi release adds one, an auto-memory guard for it becomes required through a propose-change cycle." (3) In the cross-Driver single-sourcing paragraph, the phrase that currently reads verbatim "MUST be single-sourced and ship BYTE-IDENTICALLY in BOTH Driver bundles — `livespec-driver-claude` (`.claude-plugin/hooks/`) and `livespec-driver-codex` (`livespec/hooks/`) — with each bundle's `hooks.json` `Stop` registration the thin per-runtime adapter" MUST be replaced with "MUST be single-sourced and ship BYTE-IDENTICALLY in EVERY Driver bundle — `livespec-driver-claude` (`.claude-plugin/hooks/`), `livespec-driver-codex` (`livespec/hooks/`), and `livespec-driver-pi` (its package hook location) — with each bundle's Stop-equivalent registration the thin per-runtime adapter; a Driver whose runtime exposes no Stop-equivalent event surface records that limitation in its own repository's specification and is exempt from carrying the body until the runtime grows one". (4) A new paragraph, sibling of the Codex footgun-guard paragraph, MUST be added: "**pi footgun guard (required for mutating pi automation).** The pi Driver (`livespec-driver-pi`) MUST ship a pi extension registering a `tool_call` event handler that is the behavioral port of the Claude Driver's footgun guard: it MUST block (returning pi's block decision with a reason) a tool call that would (a) pass `--no-verify` to `git commit` / `git push`, (b) set `LEFTHOOK=0` or `LEFTHOOK=false` to disable lefthook, (c) set `core.bare = true` on a checkout, or (d) edit files at a livespec primary checkout. The guard MUST be in place before the pi Driver claims any MUTATING operation (`seed`, `propose-change`, `critique`, `revise`, `prune-history`); read-only operations (`help`, `next`, `doctor`) do not depend on it. This guard is the ONE sanctioned first-party pi extension in the pi Driver — the eight operation bindings themselves MUST remain SKILL.md skills, never extensions — because the guard is a hook, and each Driver ships its hooks in its runtime's native hook mechanism (pi's is the extension `tool_call` event). Like the other Driver hook bundles, the implementation and its tests live in the Driver repo; this section states only the required surface and its behavioral discipline. The fail-open discipline above applies: a hook failure (missing interpreter, malformed input, missing config) MUST be a silent pass-through, and the guard acts only when it POSITIVELY identifies a forbidden invocation — and because pi's own default is the OPPOSITE (a `tool_call` handler error blocks the tool, fail-closed, per pi's extension error-handling behavior observed in pi v0.84.1), the guard MUST catch its own errors internally to deliver that fail-open discipline rather than inheriting pi's fail-closed default. The destructive-command controls the operation prose already carries are PRESERVED and additive to this guard — in particular `prune-history` remains explicit-user-invocation only and MUST NOT be auto-activated."

## Proposal: pi dogfooding compatibility, contracts, and constraints sections

### Target specification files

- SPECIFICATION/non-functional-requirements.md

### Summary

Adds the pi siblings of the three Codex dogfooding sections to non-functional-requirements.md — "pi dogfooding compatibility" (beside "Codex dogfooding compatibility"), "pi dogfooding contracts" (beside "Codex dogfooding contracts"), and "pi dogfooding constraints" (beside "Codex dogfooding constraints") — plus two pi scenarios beside the existing Codex scenarios, so the pi Driver path carries the same no-duplication, thin-binding, mutating-gate, and claim-acceptance discipline the Codex path does.

### Motivation

The bootstrap-pi-driver plan's spec-first carrier (epic livespec-g5h5ff, child livespec-dsnlkx): the Codex dogfooding sections are the ratified pattern for adding a runtime, and the pi Driver must inherit the same contributor-facing discipline before the livespec-driver-pi bindings and the live end-to-end exercise land.

### Proposed Changes

In `SPECIFICATION/non-functional-requirements.md`: (1) Immediately after §"Codex dogfooding compatibility", a new `### pi dogfooding compatibility` section MUST be added: "The `livespec` repository supports maintainer dogfooding from the pi coding agent through the distributed pi Driver plugin `livespec-driver-pi` (the analogue of `livespec-driver-claude` and `livespec-driver-codex`), installed as a project-scoped pi package via the committed `.pi/settings.json` per `contracts.md` §"Plugin distribution". The pi Driver ships THIN pi SKILL.md bindings over CORE's harness-neutral operation prose and wrapper CLIs; it carries no operation behavior of its own. pi dogfooding is a Driver binding, not a separate LiveSpec product command model. The authoritative command behavior remains the core-owned operation prose under `.claude-plugin/prose/<name>.md` plus the spec-side wrapper contracts under `.claude-plugin/scripts/bin/`. When a pi session receives a request for a `/livespec:*` operation (surfaced in pi as the `livespec-<operation>` skill), the pi Driver binding MUST read the matching `.claude-plugin/prose/<name>.md` file completely before acting; when that prose calls for a CLI, it MUST invoke the configured wrapper under `.claude-plugin/scripts/bin/` with explicit argv. The pi Driver bindings MUST NOT copy operation prose, wrapper files, or built-in templates, and MUST NOT point at `.claude-plugin/skills/*`; core intentionally ships no `.claude-plugin/skills/` tree. The pi Driver exposes the FULL eight spec-side operations, INCLUDING the mutating ones (`seed`, `propose-change`, `critique`, `revise`, `prune-history`). Mutating pi automation is gated on the pi footgun-guard `tool_call` extension required by `contracts.md` §"Driver-shipped hooks"; until that guard is in place a pi Driver MUST NOT claim mutating operations. All destructive-command controls from the core prose are preserved — in particular `prune-history` remains explicit-user-invocation only. Under the sibling-repo topology, each orchestrator plugin's repository is responsible for its own pi Driver mapping; implementation-side workflows MUST NOT be promoted into `livespec` by pi compatibility work." (2) Immediately after §"Codex dogfooding contracts", a new `### pi dogfooding contracts` section MUST be added: "Core is distributed to pi as a resource-less git package per `contracts.md` §"Plugin distribution" — no pi manifest, no pi resource directories, the same `prose/` and `scripts/` every other runtime binds. The pi Driver `livespec-driver-pi` is installed project-scoped via the committed `.pi/settings.json` and binds those core files at runtime; this repository ships NO project-local `.pi/skills/` or `.agents/skills/livespec-*` adapter directories for the core operations — the repo-local adapter model stays retired in favor of the distributed Driver. Each pi Driver binding MUST be thin: it reads the named core prose file completely, follows that prose for behavior and failure handling, invokes the named wrapper when wrapper-backed, and does not copy operation-specific prose sections. The pi Driver carries all eight operations; the mutating subset is gated on the pi footgun-guard extension per `contracts.md` §"Driver-shipped hooks". The detailed pi mapping for orchestrator-plugin commands is owned by each orchestrator plugin's own spec, consistent with §"pi dogfooding compatibility". pi compatibility verification is performed with separate pi processes against the installed distributed Driver. The acceptance bar is: the committed `.pi/settings.json` carries both package entries (core and the pi Driver), the packages are present in the project's `.pi/git/` install locations (or the user-scope equivalents), AND a non-interactive `pi -p` invocation with trust established drives a `/livespec:*` operation through the pi Driver and core prose WITHOUT relying on any repo-local adapter directory or an `AGENTS.md` mapping. The expected result is that pi names the bound core prose file (`.claude-plugin/prose/<name>.md`) and, for wrapper-backed operations, the matching `.claude-plugin/scripts/bin/...` wrapper it invokes. A separate human-discoverability claim MUST drive pi's interactive skill surface (the `/skill:` command completion or the startup skills listing) and verify the `livespec-<operation>` skills appear. Temporary pi package registrations used for testing MUST be removed after the test unless the user explicitly asks to keep them." (3) Immediately after §"Codex dogfooding constraints", a new `### pi dogfooding constraints` section MUST be added: "pi compatibility for repository dogfooding MUST NOT duplicate LiveSpec operation prose, Python wrappers, or built-in specification templates. Core prose under `.claude-plugin/prose/<name>.md` and wrapper CLIs under `.claude-plugin/scripts/bin/` are the shared source of truth; the pi Driver bindings MUST remain thin over those files and MUST NOT copy or restate operation-specific steps, failure handling, output schemas, or wrapper behavior in a way that can drift. The pi Driver MUST NOT point at `.claude-plugin/skills/*` or require that tree to exist. Core MAY claim pi-native plugin support only once the pi package registration creates the committed `.pi/settings.json` entries AND a separate non-interactive `pi -p` invocation can drive a `/livespec:*` operation through the registered packages without relying on any repo-local adapter or `AGENTS.md` mapping; the skill-command expansion (`/skill:livespec-<operation>`) MUST be verified in the non-interactive path itself, not assumed from its documented interactive behavior. The mere existence of package entries in `.pi/settings.json` does NOT by itself license the claim — pi's trust gate means an untrusted non-interactive invocation silently ignores project packages, so the live drive is the only evidence that counts. pi dogfooding MUST work without installing or modifying global/system packages beyond the per-user pi CLI installation itself; the package installs are project-scoped. Temporary pi package registrations used for testing MUST be removed after the test unless the user explicitly asks to keep them. The pi Driver surface MUST preserve every destructive-command control from the core prose. In particular, `prune-history` remains explicit-user-invocation only, and pi MUST NOT infer or auto-activate it from a generic mention of history. Mutating pi operations (`seed`, `propose-change`, `critique`, `revise`, `prune-history`) MUST NOT be exercised unless the pi footgun-guard `tool_call` extension required by `contracts.md` §"Driver-shipped hooks" is in place." (4) In the §"Scenarios" region beside the existing Codex scenarios, two new scenarios MUST be added. First, `### Scenario: pi drives a spec-side operation through the installed packages`: "Given a livespec-governed project whose committed `.pi/settings.json` declares the core package and the pi Driver package at the release branch ref— And a pi project-trust decision is established for the project — When a non-interactive `pi -p` invocation names the `livespec-next` skill — Then the pi Driver binding reads core's `prose/next.md` and invokes the configured next wrapper under `.claude-plugin/scripts/bin/` — And the operation resolves without any repo-local adapter directory or `AGENTS.md` mapping." Second, `### Scenario: an untrusted non-interactive pi invocation resolves no project packages`: "Given a livespec-governed project whose committed `.pi/settings.json` declares the core and pi Driver packages — And no pi project-trust decision exists for the project and the global default is not always-trust — When a non-interactive `pi -p` invocation names a `livespec-<operation>` skill without a per-run approve flag — Then pi ignores the project-local packages and the operation does not resolve — And the correct operator remedy is establishing trust, never copying operation content into the project."
